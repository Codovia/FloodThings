# CONSTRAINTS.md

**Project:** FloodPulse
**Status:** Active. These constraints are non-negotiable throughout the project.

Every contributor (human or AI agent) must read this before writing code. If a proposed change violates any rule here, it does not ship — no exceptions for deadlines.

---

## Data integrity

- Never fabricate, simulate, or invent an environmental observation — not even temporarily, not even in development.
- Never present random values (`np.random`, formula-generated, etc.) as real measurements.
- Never hardcode environmental features (slope, river distance, flood counts, drainage scores, groundwater depth) as static per-district values. These must be derived from legitimate spatial/temporal data sources.
- Every real dataset must have provenance: where it came from, when it was retrieved, what transformation produced it.
- Missing data must remain explicitly missing or unknown. It must never silently become zero, a median, a mean, or a backfilled stale value shown as current.
- Official data (IMD/CWC/NRSC warnings) and AI predictions must never be displayed as the same thing.
- A hazard map is a modeled estimate, not ground truth.
- An unverified citizen report is never treated as ground truth.
- Data source and retrieval metadata must be preserved at ingestion.

### Data classification

Apply to every important field:

| Class | Meaning |
|---|---|
| REAL | Directly retrieved from a legitimate source |
| DERIVED_FROM_REAL | Calculated from real observations; transformation documented |
| MODEL_OUTPUT | Generated by an ML model |
| USER_REPORTED | Submitted by a citizen — never auto-treated as ground truth |
| UNKNOWN / UNVERIFIED | Cannot currently be traced or validated |

Decision rules:

```
DATA AVAILABLE                    → IMPLEMENT
DATA DERIVABLE FROM VALID DATA    → IMPLEMENT + DOCUMENT
DATA UNAVAILABLE                  → MARK UNAVAILABLE
DATA UNVERIFIED                   → MARK UNVERIFIED
DATA WOULD HAVE TO BE INVENTED    → DO NOT IMPLEMENT
```

## Machine learning

- Do not choose the final model before the dataset is validated.
- Do not create fabricated training data — not synthetic rainfall, not formula-generated flood labels, not invented reservoir levels.
- Train/test splits must be time-based. Never random-split a time-series problem.
- No spatial leakage between train and test sets.
- The ML target must come from legitimate historical flood-event records — never a hand-written formula presented as a label.
- No unexplained heuristic risk scores presented as ML predictions.
- Every dataset version and model version must be recorded and reproducible.
- Validation methodology must be documented: metrics, split strategy, holdout period.

---

## GIS / location

- Use authoritative administrative boundaries (from KGIS, LGD, Survey of India, or equivalent verified source). No fallback rectangles or approximated centroids.
- Preserve and document CRS at every spatial operation.
- Do not treat latitude/longitude degrees as kilometres.
- Spatial joins must use actual geometries, not hardcoded lookup tables.
- River distances must be calculated geometrically against real river vector data, not hand-entered.
- Slope must be derived from a legitimate DEM (e.g., SRTM), not hardcoded.
- Coordinate reference system must be validated at every spatial join.

---

## Safety

- AI predictions and official government warnings must always be visually and semantically separated.
- Community/citizen reports must be clearly labeled as unverified.
- Unknown shelter occupancy must not be interpreted as available capacity.
- Stale or unavailable data must be displayed honestly — never hidden or silently replaced.

---

## Engineering

- Secrets (`.env`, tokens, passwords, API keys) must never be committed to Git.
- Environment-specific configuration belongs in `.env` files outside version control.
- Database passwords must not be hardcoded in source code.
- Changes must be testable and tested before claiming completion.
- Agents must inspect the current state before modifying anything.
- One logical change per task. No large blind AI-generated rewrites.
- No unnecessary architecture complexity: no Kubernetes, Kafka, microservices, blockchain, native mobile app, chatbot, SMS, or email unless explicitly approved.
- Small commits with descriptive messages.
- Documentation must be updated when decisions change.
